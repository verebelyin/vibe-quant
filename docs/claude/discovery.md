# Discovery pipeline

Read before running discovery, interpreting or comparing its results, or changing discovery, fitness or the overfitting gates. Experiment history: [`../discovery-journal.md`](../discovery-journal.md).

## Current behaviour
- Discovery and screening share one code path (`NTScreeningRunner` → `StrategyCompiler`); a champion replays exactly within one run when `eval_windows=1`.
- **Liquidation is an opt-in overlay, OFF by default** (`liquidation_mode` `off|isolated|cross`, leverage a whole number in `[1,125]` (default 10); CLI `--liquidation-mode` / `--leverage` (deprecated `--liquidation-leverage`), API `liquidation_mode` + `leverage` (deprecated `liquidation_leverage` alias), UI: a **Liquidation** Off/Isolated/Cross select plus an always-visible **Leverage (1-125)** input; the screening venue runs at `parameters.leverage` in every mode; promote/replay inherit the parent). There is **no penalty term and no gate**; with the mode on, fitness reads the liquidation-adjusted metrics (the same formula, recomputed from the truncated ledgers), and the run records `notes.liquidation = {mode, leverage}` and champion/rejection/holdout rows carry `liquidation_count` / `liquidation_forfeited`. With the mode off no `liquidation*` key appears; at the default leverage 10 the numbers are byte-identical to before **at execution bars <= 8h** (on 1d, mode-off funding follows the refined exit since 2026-10-17 — see the comparability break), while a mode-off run at `L != 10` runs the venue at `L` (`screening/nt_runner.py`) — identical for strategy 239 at 1x/125x, not guaranteed for every strategy.
- **Position sizing is a run-level setting, never a gene** (policy `leverage-not-a-gene` applies the same way: sizing is chosen per run, never evolved). CLI `--max-position-pct` / `--risk-per-trade` (API top-level `max_position_pct` / `risk_per_trade`), defaults 0.5 / 0.02; stored only when non-default. The run records `notes.sizing` and promote/replay inherit it (a present-but-unreadable `notes.sizing` is a 409 with no rows). A sweep key naming a sizing field (incl. dotted spellings like `max.position.pct`) is rejected.
- **Margin limit and bankroll grid are opt-in, OFF by default.** The run-level **margin limit** `--max-margin-pct` (API top-level `max_margin_pct`, a fraction in (0, 1]) caps the margin in use (open positions + pending entries + the candidate entry) at each run's leverage via the shared `vibe_quant/margin_limit.py` rule (SPEC § Position sizing); the run records it in `notes.sizing` and promote/replay inherit it. The optional **bankroll grid** replaces the single run-level setup: CLI `--bankroll-modes` (comma-separated, `isolated`/`cross` only) + `--bankroll-leverages` (whole numbers 1–125) + `--bankroll-max-margin-pcts` (numbers in (0, 1]) — all three together — or API `bankroll_grid = {modes, leverages, max_margin_pcts}`. Cells = product(modes in `(isolated, cross)` order, sorted leverages, sorted cushions), deduplicated, at most 12, each able to margin the run's cap at its own leverage; a grid is **exclusive** with the run-level `--liquidation-mode` / `--leverage` / `--max-margin-pct`. Discovery searches every cell × seed and picks the best strategy and cell together; every cell's evaluations count as trials for DSR (**N = Σ over cells × seeds**), so a bigger grid makes passing harder and costs proportionally longer. Each champion records its cell (`top_strategies[i].bankroll = {liquidation_mode, leverage, max_margin_pct}`, with `notes.bankroll_grid = {cells, n_cells}` and no run-level `liquidation`/`leverage`/`sizing.max_margin_pct`); promote/replay inherit exactly that cell (a missing/invalid one is a 422), and the full-range headline is measured at the champion's own cell. With **no grid** the run is today's single-setup path, unchanged.
- **Fail closed on liquidation data:** a missing or incomplete MARK 1m series, an unpriceable open survivor, or a fill/funding/cash flow at the run end fails the run with `LiquidationIntegrityError: liquidation_mode='isolated': ...` (never a `-999`/`-inf` row), at every stage (train, holdout, cross-window, WFA, full-range).
- **Parity limit (bead vibe-quant-vjno2):** fixed 2026-10-15 (see the comparability break below). Screening used to overstate liquidation hits when a stop sat inside the liquidation distance — screening ended exposure at the strategy-bar close while validation's 1m stop fill was earlier (was: strategy 239, BTCUSDT 4h, isolated 50x, screening 18 hits vs validation 0; at 125x both reported 60). In screening/discovery, with the overlay on and an execution timeframe above 1m, a resting STOP_MARKET/LIMIT exit is now timed at the first 1m LAST bar inside the strategy bar (after the order went live) that reached its level (stop: touch counts; limit: must trade through), so the scan stops at that minute. Mode-on screening/discovery hit counts and liquidation-adjusted metrics now change, and discovery fitness reads those metrics, so it changes too. Post-fix parity (MEASURED, job 20261015-honest-safe verifier, same window): 50x screening 0 hits vs validation 0 (screening return 0.159784359286041, 67 trades, `exit_timing` refined 66 / kept_bar_close 0); 125x 60 vs 60 with matching hit timestamps.
- **`path_divergence`:** a hit truncates the hit position's ledger, but NT's later positions are kept and re-sized as they were; their sizing used pre-liquidation equity and missed re-entries cannot be reconstructed, so the scan flags `path_divergence` (set when there is at least one hit). Every reported metric is recomputed from the truncated ledgers, not NT's raw path.
- **Peak RSS ≈ 1.15 GB per worker with the mode on** (measured on a mode-on run); mode off is unchanged.
- **Fitness** = 35% Sharpe + 25% (1 − MaxDD) + 20% PF + 20% Return; 0 below 50 trades.
- **`eval_windows` (default 3) stores WORST-of-N sub-window metrics** (min Sharpe/return/PF, max DD; each window needs ≥ max(1, min_trades // (2N)) trades). A full-window replay legitimately differs (`ReplayResponse.metrics_note` explains it).
- **Gates fail closed** (0 champions + `guardrail_rejections`); every run keeps a default 20% holdout used once as the final gate.
- **Bootstrap-CI floor** (statistic = t-stat mean/std·√n): 1m 0.5, 4h/1d 0.0 (1.0 is unpassable at ~50–180 trades/yr). Every champion forced past it with `no_bootstrap_ci=true` and then validated collapsed (Batch 41: 5.40 → −2.78; Batch 43 RAMS: 0.59 → −0.36); treat a flagged strategy as overfit.
- **DSR gate N is cumulative:** this run's evaluated strategies + prior non-mock discovery runs with the same timeframe and an overlapping train window (`notes.dsr_trials.gate_n/prior_n/prior_run_ids`). On a DB error it falls back to the run-only N and records `prior_error: true`. The gate and the worst-mode per-symbol PSR floor test the champion's **mark-to-market** daily series (the same series the buy-and-hold gate reads; see the 2026-10-12 comparability break), and a missing MTM series fails DSR closed.
- **Buy-and-hold gate (fail closed):** champions must beat the directional equal-weight, daily-rebalanced buy-and-hold Sharpe of their symbols over the train window, measured on the mark-to-market daily series (`notes.buy_hold_gate`); `symbol_agg=worst` also checks each symbol against its own benchmark. Skips only for a non-NT backtest fn; `--no-buy-hold-gate` disables.
- **Seed:** `--seed N` (CLI; auto-drawn otherwise, persisted in `notes.seed`) replays a run exactly with the same config and code.
- **Fails loudly:** an all-errored eval batch raises `DiscoveryEvaluationError` → run `failed`, not "0 champions".
- Validation's consistency check (`validation/consistency.py`) flags screening→validation collapse against the same window; holdout-validated champions are compared on their holdout metrics.
- **Compiler version hash** (`compiler_version_hash()`, stored in run notes for staleness) changes with indicator/codegen changes: `bd recall discovery:compiler-hash`. Champion rankings: `bd recall discovery:champions`.
- **HYPE's short history constrains multi-symbol runs:** HYPE has ~16.6 months (2025-05-30 10:30 → 2026-10-16, ~504 d; ~403 d train / ~101 d holdout at the default 20%, `eval_windows=3` → ~134 d per window; `OWN_TREND(200)` is NaN for its first ~200 daily bars). A multi-symbol run including HYPE must start >= 2025-05-31, which drags BTC & co. into the same short window (fill-tick coverage fails closed otherwise); HYPE-only champions are low-confidence (user decision 2026-10-17). HYPE settles funding every 4h, so its one archived venue skip (2026-06-24 04:00) is charged as a single flagged fallback (0.01% per 8h scaled 4/8 = `0.00005 x notional`), counted in `funding_fallback_settlements`.
- **1m is slow:** Rust-native indicators (SMA/EMA/CCI/STOCH/ATR) run ~10× faster than pandas-path ones (ADX/MACD/BBANDS/KAMA).
